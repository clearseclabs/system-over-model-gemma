# Triage T0100: Incorrect pointer cleanup in failed request registration

- **File**: `svc.c`
- **Verdict**: INVALID
- **Confidence**: 0% [IIU→I]

## Finding

Incorrect pointer cleanup in failed request registration

---

## Triage rounds

### Round 1: ❌ INVALID

**🎯 Crux:** svc_reg frees netid on every failure path and only allocates svc_callout when malloc succeeds; no dangling pointer is ever left for the dispatcher to dereference.

The reported flaw claims that on failure paths in svc_reg the newly allocated svc_callout structure is not freed, leading to memory leaks or stray pointers that the dispatcher might later dereference.  A careful data‑flow trace of svc_reg shows the following:

1. **Netid allocation** – When a netid is required the code performs a strdup.  If this strdup fails and flag==1, svc_reg immediately returns FALSE without allocating a callout, which is correct.
2. **Existing callout check** – svc_find is invoked under the pool lock.  If a callout already exists, the code frees the netid (if any) and, if the dispatch function matches, jumps to rpcb_it (after unlocking).  No new callout is allocated.
3. **Allocation failure path** – If svc_find returns NULL, malloc is attempted.  The code explicitly checks for a NULL return: if (s == NULL) { if (netid) free(netid); mtx_unlock(...); return FALSE; }  Thus the netid is freed and no dangling pointer remains.
4. **Successful registration** – On successful allocation the structure is inserted into the pool and the caller releases the lock and returns TRUE.

In every failure case the netid is freed, and the svc_callout structure is only allocated when malloc succeeds.  Therefore there is no scenario in which a partially constructed svc_callout is left allocated but unreachable.  The purported “s->sc_dispatch == dispatch” duplicate check does not create an allocation; it merely re‑uses the existing structure.

Because the code does not leave stray pointers and memory consumption is limited by the number of concurrent registrations, the issue—a memory leak—does not constitute an exploitable security vulnerability.  Attacker‑reachable code paths do not result in unsafe dereferences or other undefined behaviour.

Thus the scanner’s finding is a false positive.  The lesson is that memory‑leak advisories should not be treated as security issues unless they enable an attacker to reach uninitialised or dangling pointers that could be exploited.

### Round 2: ❌ INVALID

**🎯 Crux:** netid freed on every failure path in svc_reg before return

svc_reg correctly frees any allocated netid on every failure path
- If the strdup for netid fails, svc_reg returns FALSE before allocating a callout.
- If svc_find finds an existing callout, the code frees netid (if allocated) and either:
  * jumps to rpcb_it when the dispatch function matches – no new callout is allocated;
  * or returns FALSE.  In both cases netid is already freed.
- If malloc for the svc_callout fails, the code frees netid (when non‑NULL), releases the lock and returns FALSE.
Thus there is no scenario in which a partially constructed svc_callout is leaked or a dangling pointer remains for the dispatcher to use.  The caller of svc_reg is kernel code; an attacker cannot invoke it directly, so the reported issue is not attacker‑reachable.  The flaw described by the scanner therefore does not constitute a security vulnerability and is a false positive.

The defense that ensures this behaviour is the unconditional free(netid, M_RPC) statements before each return in the failure paths.  The code paths were verified via grep, confirming that the free occurs in every branch where netid has been allocated.

Conclusion: The finding is INVALID (a memory‑leak but not attacker‑reachable).
