[ARBITER] The “overflow” relies on the request size `rq_size` yielding a very large negative or positive long value that, when added to `sp_space_used`, wraps around a 32‑ or 64‑bit unsigned long. In practice `rq_size` is computed as `sizeof(*r)+m_length(args,NULL)`. The `m_length` routine returns an unsigned 32‑bit count that is bounded by the kernel’s configurable maximum RPC message size (typically a few megabytes). Therefore `rq_size` can never exceed `LONG_MAX`, and delta can never be large enough to wrap an unsigned long counter whose high‑watermark is set to `nmbclusters*MCLBYTES/4` (on NetBSD this is well below a gigabyte). The atomic_fetchadd_long call simply increments or decrements the counter by a value that is far below the wrap threshold.  Consequently the claimed integer overflow cannot be triggered in normal operation and does not expose a denial‑of‑service path.
