### Round 3: ❌ INVALID

**🎯 Crux:** The potentially uninitialised transport members are never read in a context that processes attacker supplied data, and mem_alloc zeroes the memory that the code relies on.  Consequently there is no attacker‑reached vulnerability.

svc_xprt_alloc returns two objects that are never zero‑initialised.  The fields that are mentioned in the report – xp_flags, xp_netid, xp_p3, xp_socket – are part of the server‑side transport state.  The only code that reads or writes those fields before they are explicitly initialised is the internal RPC registry helpers (svc_raw_create, svc_raw_attach, svc_bind, svc_reg, etc.) which are invoked only by the process that creates the RPC server.  An attacker can’t feed data that reaches those helpers; all data coming from clients is through the XDR decoding code in svc_getreq, and the transport structure is never inspected for client‑supplied content.  Therefore the un‑initialised memory cannot be triggered by an external party, nor can it crash or leak data in a way that can be abused.  On top of that, the kernel implementation of mem_alloc (see sys/rpc/types.h) actually allocates memory with either calloc or M_ZERO, so the allocated blocks are zeroed out.  The result is that the potential bug affects only internal state that is never exposed to untrusted input, and it does not create a meaningful security vulnerability.

Crucial evidence:
* The definition of mem_alloc in sys/rpc/types.h uses either malloc(M_WAITOK|M_ZERO) or calloc(1,bsize), meaning the structures are zeroed on allocation.
* The transport fields are only read in trusted‑only helper functions; none of those functions are called with data derived from the network.

Thus the finding is a code‑quality issue rather than a security problem.

### Round 4: ❌ INVALID

[ARBITER] `svc_xprt_alloc` uses `mem_alloc`, which in NetBSD’s `<rpc/types.h>` expands to `malloc(bsize, M_RPC, M_WAITOK|M_ZERO)`. The allocation therefore yields zero‑initialised memory. All fields of `SVCXPRT` and its `SVCXPRT_EXT` extension are set to known values (or zero). Subsequent code accesses these fields only after they are safely initialised or checks that the field is non‑NULL before use. No attacker‑controllable input can force a read of uninitialised memory, nor is any field left undefined before first use. Thus the claim of an uninitialised‑memory vulnerability is incorrect. The evidence from the source shows proper zero‑initialisation and safe usage, so the finding is not a valid vulnerability.
