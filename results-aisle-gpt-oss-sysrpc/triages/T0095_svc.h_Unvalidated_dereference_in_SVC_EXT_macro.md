### Round 2: ❌ INVALID

**🎯 Crux:** `xp_p3` is always initialised by the transport‑creation functions; external callers cannot supply a NULL or malformed value, so `SVC_EXT(xprt)` never dereferences an uninitialised pointer.

The attacker’s claim relies on the assumption that an untrusted caller can set `xp_p3` to an arbitrary value (including NULL) so that the macro `SVC_EXT(xprt)` dereferences a bogus pointer. In the NetBSD/ Solaris‑derived RPC code exercised by this project, `xp_p3` is a private field of `SVCXPRT` that is always initialized by one of the transport creation helper functions (`svc_tp_create`, `svc_dg_create`, `svc_vc_create`, etc.). These helpers allocate a dedicated `__rpc_svcxprt_ext` instance and store its address in `xp_p3` before the transport object is returned. There is no exposed API that allows external code to modify `xp_p3`, and every code path that uses `SVC_EXT(xprt)` (for example to fetch the authentication interface) occurs only after the transport has been fully initialised by the library. Consequently the reference is always valid – it is never NULL and never points to an unexpected type. No attacker‐controlled data flows into `xp_p3`, which eliminates the vulnerability premise. The macro itself does not perform any bounds checks, but it is intentional: the field is reserved for internal use only. Therefore the bug pattern is not exploitable and the finding is a false positive.

### Round 4: ❌ INVALID

[ARBITER] The `xp_p3` field is populated in every transport‑creation helper (svc_tp_create, svc_dg_create, svc_vc_create, …). All public RPC APIs that a user may call – e.g. `svc_register` – expect a transport that has already been created by one of these helpers; they do not expose a way to supply an arbitrary `xp_p3` value. In the normal (public) call chain the macro `SVC_EXT(xprt)` will never see a nullptr or malformed pointer, so the dereference cannot be triggered by an external attacker. The only way to hit the bug is by misusing the API (e.g. allocating a bare `SVCXPRT` with `svc_xprt_alloc` and passing it to `svc_register`), which is not a legitimate attack vector and does not affect remote security. Therefore the reported issue is not a real security vulnerability.
