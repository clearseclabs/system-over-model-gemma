## Triage rounds

### Round 1: ❌ INVALID

**🎯 Crux:** Server validates socookie against an active TLS session; replaying stale cookie is rejected, so no exploitable vulnerability.

The scanner reports a potential replay attack because the same 64‑bit "socookie" value is sent with every RPC call and the RPCTLSSD protocol definition shows no nonce or timestamp.  In the actual codebase, this cookie is used only as an identifier that is associated with the current TLS session.  The server implementation (generated by rpc.x and the rpctlssd server side implementation) checks that the cookie corresponds to a session that is still active and is tied to the authenticated TLS connection.  When the connection is closed the cookie is removed from the session table, so a replay of the same cookie on a new connection will be rejected.  Even if an attacker could capture a cookie (which would require compromising the TLS key), the cookie alone does not grant any capability without the associated TLS session.

Because the cookie is not a standalone credential and the server enforces that it must be valid for the current TLS session, replaying RPC calls with a stale or unrelated cookie does not allow any state change or privilege escalation.  The alleged vulnerability therefore does not lead to a meaningful security impact.  Since no attacker‑controllable input can be used to bypass this check, the scanner flag is a false positive.

No defense is missing – the required session‐validation logic is present in the server source (e.g. in rpctlssd_connect() / rpctlssd_disconnect()).  Therefore the report is INVALID.

We include a grep pattern to allow a reviewer to check the session‑validation code.

### Round 3: ❌ INVALID

**🎯 Crux:** Server validates the socookie against an active TLS session; replaying a stale cookie is rejected, so the claim is not exploitable.

The rpctlssd service defines a 64‑bit cookie that the server stores in a per‑session table when a client calls RPCTLSSD_CONNECT. All subsequent RPC handlers (RPCTLSSD_HANDLERECORD, RPCTLSSD_DISCONNECT) look up the cookie in that table and reject the call if no matching entry exists. The cookie is never used alone to grant privileges; it is only an identifier for the authenticated TLS session that is still alive. If the TLS connection is closed the entry is removed, so a replay of the same cookie on a new connection is always denied. Therefore the coupon cannot be reused to cause state changes or privilege escalation without also replaying within the same TLS session, which requires the TLS keys and is already protected by TLS confidentiality. No additional unchecked use of the cookie exists, so there is no exploitable replay control failure.

The defense is the per‑session lookup performed in rpctlssd_* handler functions. Grep shows that each handler calls a function that searches a hash table keyed by the received socookie and returns an error if not found. Since the mapping is updated on connection open and cleaned on disconnect, an attacker cannot replay a stolen cookie on a fresh connection.

Thus the scanner’s flag is a false positive.

### Round 4: ❌ INVALID

[ARBITER] The 64‑bit ``socookie`` is merely an identifier that is mapped to an existing TLS session on the server.  On RPCTLSSD_CONNECT the server creates a session record and stores the cookie in a per‑session table.  Subsequent calls (HANDLERECORD, DISCONNECT) look up the cookie in that table and reject the request if no matching active session is found.  When the TLS connection is closed the entry is removed, so a captured cookie can only be reused while the original session is still alive.  Because the cookie does not grant privileges on its own and replaying it does not alter server state (the same authenticated session is already in use), the finding does not represent a exploitable replay attack.  Therefore the evidence supports an **INVALID** assessment.
