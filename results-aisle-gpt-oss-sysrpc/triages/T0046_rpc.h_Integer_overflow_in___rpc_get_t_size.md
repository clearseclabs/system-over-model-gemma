Integer overflow in __rpc_get_t_size()

## Triage rounds

### Round 1: ❓ UNCERTAIN



### Round 2: ❌ INVALID

**🎯 Crux:** The code that allocates the buffer for an RPC message checks that the size returned by __rpc_get_t_size() is <= UDPMSGSIZE (8800) and aborts the operation if it is not, preventing any exploitation of the integer overflow.

The function __rpc_get_t_size() merely sums three 32‑bit ints and casts the result to u_int.  In theory an attacker supplying very large values for the RPC request’s program identifier, procedure number or other fields could cause the addition to wrap around, yielding a small buffer size that is then used for serialisation.  The inputs, however, come from the client request headers and are therefore attacker‑controlled.  The crucial question is whether the RPC library guards against this overflow before memory is allocated.

In the repository the allocation of the buffer used for an outgoing RPC request is guarded by the maximum UDP message size.  After computing the size, the code checks against UDPMSGSIZE (8800) and, if the computed value exceeds this limit, it aborts the call rather than allocating.  This check appears in the client path in clnt_call() (and the equivalent server path) immediately after the call to __rpc_get_t_size().  Because the maximum allowed size is respected, a wrapped small value would in fact trigger the guard and prevent any unchecked allocation.  The check is a true defensive boundary, not merely a comment.

Hence, while the integer addition can overflow, the code path that uses the result imposes a hard size limit that prevents an attacker from gaining any benefit from the overflow.  The vulnerability is effectively mitigated by this boundary check.

Verdict: The potential overflow is neutralised by an explicit size guard; therefore the bug is not a real, attacker‑reachable vulnerability.


CRUX: The code that allocates the buffer for an RPC message checks that the size returned by __rpc_get_t_size() is <= UDPMSGSIZE (8800) and aborts the operation if it is not, preventing any exploitation of the integer overflow.

### Round 4: ❌ INVALID

[ARBITER] The only place where the size returned by `__rpc_get_t_size()` is used for allocation is followed by an explicit check that the value does not exceed `UDPMSGSIZE` (8800). In all code that we have examined the third argument to `__rpc_get_t_size()` is either the constant `UDPMSGSIZE` or a value that is already bounded by this constant. Thus even if an attacker could cause an integer overflow that wraps the resulting sum to a very small value, that value would still pass the “<= UDPMSGSIZE” test and the allocation would be made for a buffer that is large enough for the legitimate, bounded message size. Furthermore, any request that could be built with oversized program/ procedure numbers would already be limited by the underlying transport (UDP/JMP) to the same size. Because no code path allocates a buffer based purely on an overflowed sum of arbitrary client‑supplied integers, there is no realistic write‑past‑end or other exploitable effect. Therefore the reported medium‑severity finding is not a valid vulnerability.
