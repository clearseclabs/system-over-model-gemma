# Scan: pmap_prot.h

**Security Analysis – `pmap_prot.h`**

`pmap_prot.h` is a public header that defines the *interface* of the Sun RPC `rpcbind` service (portmap).  While the header itself contains no executable code, its definitions dictate how other modules (e.g., the XDR helpers, the RPC service routines, and third‑party applications) interpret packets received on port 111.  Consequently, subtle mismatches or missing checks in this API can result in memory corruption, integer over‑flows, or even remote execution when an attacker crafts a malformed packet.  The findings below focus on how the exposed types, constants, and function prototypes can be abused, rather than searching for bugs in the header’s own (non‑existent) implementation.

| **Severity** | **Title** | **Function/Context** | **Description** |
|--------------|-----------|---------------------|-----------------|
| **Critical** | **Inconsistent unsigned‑long mapping to XDR’s 32‑bit integers** | `struct portmap` (and `struct pmaplist` via `xdr_pmaplist`) | The protocol specifies the fields `pm_prog`, `pm_vers`, `pm_prot`, `pm_port` as *unsigned long*.  In many 64‑bit systems `unsigned long` is 64 bits, while XDR’s `unsigned int` (and the C‐type used by `xdr_*`) is 32 bits.  An attacker can send values > 2³²‑1; on the server side the XDR routine will truncate or sign‑extend, producing a different numeric value for the program/port number.  If the server logic then uses the truncated value to look‑up a session, it may resolve to the wrong entry or fail to find a valid entry, leading to denial‑of‑service or unintended privilege escalation.  A buggy implementation that incorrectly casts the XDR data back to `unsigned long` may also write past the intended buffer when the 64‑bit value is stored in a 32‑bit field, resulting in heap corruption. |
| **High** | **Missing null‑pointer checks in XDR helpers** | `xdr_portmap()`, `xdr_pmaplist()`, `xdr_pmaplist_ptr()` | All three functions are declared to return `bool_t` but their parameter types are pointer references (`XDR *`, `struct portmap *`, `struct pmaplist *` or **double** pointer).  The RPC server typically calls these helpers with pointers derived directly from the network stream.  If an attacker sends an RPC packet that causes the XDR buffer to become misaligned or under‑written, the helper may receive a `NULL` or partially‑initialized structure.  Because there are no visible null‑check guards in the interface, the callee might dereference a bad pointer, leading to segmentation fault, crash, or even arbitrary code execution if the error is transposed into a path that uses function pointers or jump tables.  The lack of defensive programming in the *declarative* API encourages implementers to omit such checks, especially in legacy code paths. |
| **High** | **Unvalidated length of the variable‑length string in PMAPPROC_CALLIT** | The comment “PMAPPROC_CALLIT(unsigned, unsigned, unsigned, string<>)” | The header does not expose an XDR routine for serialising the fourth argument of `PMAPPROC_CALLIT`.  Legacy implementations often concatenate the string and its length manually or rely on callers to provide a correctly formatted buffer.  If an attacker supplies a length value that is larger than the actual byte stream, the XDR decoder will read past the packet boundary, corrupting the `XDR` stream control structure or arbitrary memory.  Likewise, if the length is negative (when sign‐extended into a signed value before being converted to `unsigned`) the resulting write might overflow the buffer used to temporarily copy the string.  Because the protocol is “the only interface the client needs to construct an RPC packet for the dispatcher,” an exploitable mismatch between the declared size and the actual payload is a prime vector for denial‑of‑service and buffer‑overflow exploits. |
| **Medium** | **Privilege‑elevated binding to port 111** | Constants `PMAPPORT` | The header defines the well‑known port (111) that the rpcbind service must bind to.  On many operating systems, binding to a privileged port (< 1024) requires root permissions.  If an attacker can compromise the rpcbind process (e.g., via a deserialization bug in a consumer of `pmap_prot.h`), they could bind another listener on port 111 to hijack RPC traffic.  While the header itself is not a vulnerability, the contract implicitly requires the server to run with elevated privileges, which raises the risk surface for privilege‑escalation attacks. |
| **Medium** | **Potential symbol collision and macro redefinition** | `PMAPPROC_*` constants | The protocol constants are defined as simple macros without any namespace prefixing.  In applications that include other Sun RPC headers, a conflicting macro may silently override the intended value, causing subtle logic errors (e.g., registering the wrong procedure number).  A malicious build environment might inject a redefining header that changes the semantics of RPC calls without the programmer’s knowledge, leading to protocol confusion and possible supply‑chain attacks. |
| **Low** | **Absence of bounds checking for pointer chain in pmaplist** | `struct pmaplist` | The `pml_next` pointer is used by `xdr_pmaplist()` to walk an arbitrarily long linked list.  If an attacker crafts a list with an unusually large depth or forms a cycle (by putting the same pointer value in multiple nodes), a naïve implementation that blindly follows the pointers may end up in an infinite loop or traverse a huge number of nodes before returning.  This can lead to denial‑of‑service via excessive memory usage or CPU consumption.  While the XDR routine typically detects recursion depth limits, older or custom implementations might not. |
| **Low** | **Limited documentation of type aliasing** | `struct portmap` members | The use of `long unsigned` for all fields can be obscured by different type aliases across platforms (`unsigned long`, `rpcprog_t`, etc.).  Mis‑interpretation of the type can lead to compiler warnings that are ignored, producing subtle mismatches in packed data.  An attacker may exploit the resulting undefined behaviour to spoof program/port mappings and redirect RPC calls. |

**Overall Guard Strategies**

1. **Strict type size enforcement** – In the XDR implementation, always use `u_int` (32‑bit) fields inside the RPC structure, or cast explicitly before serialising to avoid silent truncation on 64‑bit machines.

2. **Robust NULL checks** – Verify every incoming pointer (`XDR *`, `struct portmap *`, `struct pmaplist *`) before dereferencing.  The helper functions should return an error code if the stream is corrupted or the pointer is `NULL`.

3. **Length‑field validation** – When handling `PMAPPROC_CALLIT`, validate that the length field is less than or equal to the remaining bytes in the XDR stream.  Reject any packet that violates this constraint.

4. **Protect privileged port** – Run the rpcbind daemon in the most restricted environment that still allows binding to port 111, e.g., using a separate system service with least‑privilege user isolation, and employ kernel mechanisms such as port‑mapping restrictions or secure‑netpair.

5. **Define namespace‑safe macros** – Prefix all protocol constants with `PMAP_` or use an `enum` to avoid accidental redefinitions.

6. **Sanity checks for linked lists** – Limit the depth of the `pml_next` chain (e.g., a cap of 65536 nodes) and detect cycles to avoid denial‑of‑service attacks.

**Conclusion**

While `pmap_prot.h` itself contains no executable logic, its public API specifications give attackers a stable target for crafting malformed RPC packets and inducing undefined behaviour in the rpcbind implementation.  The most critical risk stems from the mismatch between `unsigned long` in the C structure and XDR’s 32‑bit integers, which can lead to truncation or memory corruption.  Coupled with missing null/length checks in the helper functions, these issues can be exploited for arbitrary memory corruption or denial‑of‑service.  Addressing the above mitigations will transform the header from a contract into a robust, failure‑safe interface.
